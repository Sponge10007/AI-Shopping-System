- 涉及模块：Vue 前端、Spring Boot 后端、Python AI 服务、跨服务接口

## 2. 修复背景

本次修复围绕系统的前后端数据契约、认证授权、用户数据隔离、AI 服务通信、管理员功能以及图片搜索链路展开。

审查过程中发现，系统中部分功能虽然界面上能够操作，但实际存在字段不匹配、模拟成功、固定用户、接口路径错误或跨服务数据无法传递等问题。这些问题会造成操作结果与真实业务状态不一致，严重时还会导致越权访问和用户数据串用。

本轮采用“一次修复一个问题”的方式处理，每项修复完成后均补充相应测试，并在最后执行完整回归测试。

## 3. 缺陷修复明细

### 3.1 修复前后端 JSON 字段命名不一致

#### 问题现象

前端接口统一使用 `snake_case` 字段，例如：

- `product_id`
- `image_urls`
- `access_token`
- `refresh_token`

后端 Java DTO 默认使用 `camelCase`，例如：

- `productId`
- `imageUrls`
- `accessToken`
- `refreshToken`

这会导致部分请求字段无法被后端正确反序列化，部分响应字段也无法被前端正确读取。

#### 原因分析

Spring Boot 的 Jackson 未配置统一字段命名策略，导致前后端接口契约不一致。

#### 修复内容

在后端配置中启用全局 `SNAKE_CASE` 命名策略：

```yaml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

同时更新控制器契约测试，验证商品创建、订单创建、登录响应等接口均使用 `snake_case`。

#### 主要修改文件

- `backend/src/main/resources/application.yml`
- `backend/src/test/java/com/aishop/ApiControllerContractTest.java`

#### 修复结果

前后端请求和响应字段统一，`image_urls`、`product_id`、`access_token` 等字段可以正常传输。

### 3.2 移除登录、注册、订单和支付的虚假成功结果

#### 问题现象

当后端未连接或接口请求失败时，前端会生成本地模拟结果：

- 登录失败后生成模拟登录状态；
- 注册失败后仍表现为注册成功；
- 创建订单失败后生成模拟订单；
- 支付失败后生成模拟支付成功结果。

用户可能在页面上看到“成功”，但数据库中没有任何真实记录。

#### 原因分析

前端 API 层和登录页面对写操作使用了离线降级逻辑。该逻辑适合只读演示数据，但不适用于登录、下单和支付等事务操作。

#### 修复内容

- 删除登录和注册失败时创建本地会话的逻辑；
- 删除创建订单失败时生成模拟订单的逻辑；
- 删除支付失败时生成模拟支付结果的逻辑；
- 写操作失败时向页面返回真实异常；
- 保留商品浏览等只读场景的开发降级数据。

#### 主要修改文件

- `frontend/src/views/LoginView.vue`
- `frontend/src/services/api.ts`
- `frontend/src/services/api.test.ts`
- `frontend/src/views/LoginView.test.ts`

#### 修复结果

登录、注册、下单和支付只有在后端真实成功时才会显示成功，避免前端状态与数据库状态不一致。

### 3.3 修复 AI 搜索、推荐和聊天固定使用 `u10001`

#### 问题现象

AI 搜索、图片搜索、个性化推荐和聊天功能在服务层固定使用原型用户 `u10001`。

不同用户使用系统时，搜索记录、推荐画像和聊天数据可能被错误地归入同一个用户，存在严重的数据隔离问题。

#### 原因分析

原型阶段为了快速联调，业务代码直接使用了 `CurrentUser.prototypeCustomer()`，控制器没有把真实登录用户完整传递到服务层。

#### 修复内容

- 搜索接口读取真实登录用户；
- 图片搜索读取真实登录用户；
- 推荐服务对登录用户使用真实 `userId`，匿名用户使用 `-1`；
- AI 聊天创建会话、发送消息和清空记录时使用真实用户；
- 聊天会话增加归属校验，禁止访问其他用户的会话；
- 删除业务模块中遗留的固定原型用户调用。

#### 主要修改文件

- `backend/src/main/java/com/aishop/modules/search/SearchService.java`
- `backend/src/main/java/com/aishop/modules/recommendation/RecommendationController.java`
- `backend/src/main/java/com/aishop/modules/recommendation/RecommendationService.java`
- `backend/src/main/java/com/aishop/modules/ai/AiChatController.java`
- `backend/src/main/java/com/aishop/modules/ai/AiChatService.java`

#### 新增或更新测试

#### 修复结果

不同用户的搜索、推荐和聊天数据按照真实用户隔离，跨用户访问聊天会话时返回禁止访问错误。

### 3.4 修复禁用用户仍可登录和继续使用旧 JWT

#### 问题现象

管理员页面将用户状态设置为 `DISABLED`，但登录服务只判断 `BANNED`，导致禁用用户仍可登录。

此外，用户被禁用前签发的 JWT 在有效期内仍能继续访问系统。

#### 原因分析

- 管理模块和认证模块使用了不同的用户状态常量；
- JWT 过滤器只校验令牌签名和过期时间，没有读取数据库中的实时用户状态。

#### 修复内容

- 将用户状态统一为 `ACTIVE` 和 `DISABLED`；
- 只有 `ACTIVE` 用户允许登录；
- JWT 每次访问受保护接口时查询当前用户；
- 用户不存在时返回未认证；
- 用户被禁用时返回 `403 FORBIDDEN`；
- JWT 中的旧角色不再直接使用，改为读取数据库中的最新角色；
- 对未知用户状态采用默认拒绝策略。

#### 主要修改文件

- `backend/src/main/java/com/aishop/infrastructure/persistence/entity/UserEntity.java`
- `backend/src/main/java/com/aishop/modules/auth/AuthService.java`
- `backend/src/main/java/com/aishop/common/security/jwt/JwtAuthenticationFilter.java`

#### 新增测试

- `backend/src/test/java/com/aishop/AuthServiceTest.java`
- `backend/src/test/java/com/aishop/JwtAuthenticationFilterTest.java`

#### 修复结果

被禁用用户无法重新登录，已经签发的旧 JWT 也会立即失效。

### 3.5 修复商品 AI 向量索引通知无效

#### 问题现象

商品创建、更新和下架后，Java 后端会发送 AI 索引通知，但实际调用路径和请求体与 Python AI 服务不一致。

Java 原调用形式：

```text
/index/product-created
/index/product-updated
/index/product-deleted
```

Python 实际接口：

```text
POST   /internal/v1/ai/products/{product_id}/index
DELETE /internal/v1/ai/products/{product_id}/index
```

因此商品索引通知会失败，语义搜索无法检索新商品。

#### 原因分析

Java 和 Python 服务分别按照不同接口设计实现，缺少跨服务契约测试。

另外，Python 使用 ChromaDB 的 `add` 更新已有商品，相同商品 ID 更新时可能发生冲突。

#### 修复内容

- Java 改为调用 Python 实际提供的索引接口；
- 新增和更新商品统一发送：

```json
{
  "description": "商品名称、分类、描述、标签"
}
```

- 商品下架使用 `DELETE` 删除向量；
- 商品索引文本包含名称、分类、描述和标签；
- Python 将 ChromaDB 写入方法由 `add` 改为 `upsert`；
- 商品更新时覆盖旧向量，而不是创建重复记录；
- 复用统一的 `AiServiceClient`，删除重复的 `RestTemplate` 调用代码。

#### 主要修改文件

- `backend/src/main/java/com/aishop/infrastructure/ai/AiServiceClient.java`
- `backend/src/main/java/com/aishop/modules/internal/AiIndexNotifier.java`
- `backend/src/main/java/com/aishop/modules/product/ProductService.java`
- `ai-service/app/core/labelDB.py`

#### 新增测试

- `backend/src/test/java/com/aishop/AiServiceClientTest.java`
- `backend/src/test/java/com/aishop/ProductServiceTest.java`
- `ai-service/tests/test_label_db.py`

#### 修复结果

商品创建、编辑和下架能够按照正确接口通知 AI 服务，商品更新能够覆盖原有向量索引。

### 3.6 为 Python AI 内部接口增加服务间认证

#### 问题现象

Python AI 服务的 `/internal/v1/ai/**` 接口没有认证，任何能够访问 AI 服务端口的客户端都可以：

- 写入或删除商品向量；
- 调用搜索和推荐；
- 调用聊天接口；
- 删除聊天历史。

#### 原因分析

内部接口只依赖网络隔离，没有校验共享令牌。

- 使用 `secrets.compare_digest` 比较令牌；
- Java 的 `RestClient` 自动添加内部令牌；
- Python 调用 Java 内部商品摘要接口时也添加相同令牌；
- 兼容 `AI_INTERNAL_TOKEN` 和原有 `INTERNAL_TOKEN` 环境变量；
- 更新 AI 接口文档和跨服务静态契约测试。

#### 主要修改文件

- `ai-service/app/api/py_api_server.py`
- `backend/src/main/java/com/aishop/infrastructure/ai/AiServiceConfig.java`
- `ai-service/api_readme.txt`

- `tests/pytest/test_contracts.py`

#### 修复结果

AI 内部接口由公开访问改为共享令牌认证，Java 与 Python 双向内部调用均携带令牌。

### 3.8 修复图片搜索未传递真实图片

#### 问题现象

用户上传图片后，Java 后端没有把图片内容发送给 Python，而是发送：

```text
search-upload://文件名
```

Python 视觉模块只支持：

- HTTP/HTTPS 图片 URL；
- 本地真实文件路径；
- Base64 Data URL。

因此 Python 无法读取图片，图片搜索会失败或始终降级为热门商品。

#### 原因分析

Java 和 Python 服务不共享文件系统，单独传递文件名或伪路径无法让 Python 获取图片内容。

#### 修复内容

- Java 读取 multipart 图片真实字节；
- 将图片编码为：

```text
data:image/png;base64,...
```

- 将 Data URL 通过 AI 内部接口传给 Python；
- 增加空文件校验；
- 增加 10MB 大小限制；
- 仅允许 JPEG、PNG 和 WebP；
- 校验图片文件头，防止 MIME 类型伪造；
- 后端 AI 读取超时调整为 30 秒；
- 前端图片搜索超时单独调整为 35 秒；
- 普通接口仍保持 4 秒快速失败；
- 图片识别失败时不再返回本地模拟搜索结果，而是显示真实错误。

#### 主要修改文件

- `backend/src/main/java/com/aishop/modules/search/SearchService.java`
- `backend/src/main/java/com/aishop/infrastructure/ai/AiServiceProperties.java`

### 3.10 修复 Java 调用 Python 时请求体为空

#### 问题现象

Python AI 服务日志持续显示：

```text
[AI Compare API] 收到请求字段: []
```

Java 后端随后收到：

```text
400 Bad Request: 缺少必填参数: user_id
```

#### 原因分析

Java `RestClient` 使用 HTTP/1.1 `Transfer-Encoding: chunked` 发送请求体，而 Python 基于 `BaseHTTPRequestHandler` 的实现只读取 `Content-Length`。

请求实际包含 JSON，但 Python 将其误判为空请求体。

#### 修复内容

- Python 请求读取器同时支持 `Content-Length` 和 `Transfer-Encoding: chunked`；
- 实现 chunk size、分隔符、结束块和 trailer 解析；
- 增加 12MB 请求体限制；
- 对提前结束、非法十六进制块长度和内容不完整返回明确错误；
- 对 `user_id` 同时兼容 `snake_case` 和旧的 `camelCase`；
- 增加协议级 chunked 请求测试。

#### 主要修改文件

- `ai-service/app/api/py_api_server.py`
- `ai-service/tests/test_health.py`
- `backend/src/main/java/com/aishop/infrastructure/ai/AiServiceClient.java`

#### 修复结果

Java 发送的商品对比 JSON 能被 Python 完整读取，不再出现空字段列表和缺少 `user_id`。

### 3.11 修复 AI 聊天响应传输中断导致接口 500

#### 问题现象

AI 聊天偶发出现：

```text
http.client.IncompleteRead: IncompleteRead(0 bytes read)
```

Python 接口直接返回 500，Java 将其转换为“AI 助手暂时不可用”。与此同时，AI 对比仍可正常访问 DeepSeek。

#### 原因分析

普通聊天读取 DeepSeek 分块响应时，没有捕获 `IncompleteRead`、远端断开和连接重置等传输异常。一次响应尾部缺失就会使整条聊天链路崩溃。

#### 修复内容

- 显式设置非流式请求的 `stream=false`；
- 默认关闭模型思考模式，缩短购物聊天响应；
- 默认超时由 15 秒调整为 30 秒；
- 对 `IncompleteRead`、`RemoteDisconnected`、连接重置和超时自动重试；
- 如果异常中已包含完整 JSON，则直接恢复响应；
- 重试后仍失败时转换为可读业务错误，不再泄漏 Python traceback；
- 增加可配置的重试次数、重试间隔和思考模式开关。

#### 主要修改文件

- `ai-service/app/core/llmchat.py`
- `ai-service/.env.example`
- `ai-service/tests/test_llmchat_json.py`

#### 修复结果

普通聊天对短暂的分块传输中断具备恢复能力，真实 DeepSeek 请求验证通过。

### 3.12 将 AI 聊天改为端到端流式输出

#### 问题现象

原聊天必须等待 DeepSeek 完整生成后才显示回答，长回复期间页面只能显示加载动画，交互体验较差。

#### 原因分析

DeepSeek、Python、Java 和浏览器之间均按完整 JSON 响应处理，没有增量传输协议。

#### 修复内容

- Python 使用 `stream=true` 调用 DeepSeek，并解析 SSE `data:` 事件；
- Python 内部接口以 NDJSON 输出 `delta`、`done` 和 `error` 事件；
- Java 使用流式响应读取 Python NDJSON，并立即转发文本增量；
- Java 新增：

```text
POST /api/v1/ai/chat/sessions/{sessionId}/messages/stream
```

- 浏览器使用 `fetch + ReadableStream`，保留 POST 请求和 JWT 请求头；
- 前端聊天气泡逐段追加内容并自动滚动；
- 流式结束后仍保存完整回答、链接和推荐商品；
- 保留原非流式接口作为兼容入口。

#### 主要修改文件

- `ai-service/app/core/llmchat.py`
- `ai-service/app/api/py_api_server.py`
- `backend/src/main/java/com/aishop/infrastructure/ai/AiServiceClient.java`

- `backend/src/main/java/com/aishop/modules/ai/AiChatService.java`

#### 修复结果

聊天回答可以从 DeepSeek 一直流式传递到浏览器，真实模型流式事件验证通过。

### 3.13 修复流式聊天显示 JSON 外壳

#### 问题现象

聊天页面曾直接显示：

```json
{"answer": "好的，我为您详细拆解一下……"}
```

当连接中断时，还可能只留下未闭合的 JSON。

#### 原因分析

内置系统提示词允许模型返回 `answer/image_list/link_list` JSON。非流式模式会在完整响应后解析 JSON，但流式模式会先把尚未完成的原始 token 显示到页面。

历史消息中的旧 JSON 也会诱导模型继续使用同一格式。

#### 修复内容

- 流式聊天单独增加“只输出用户可见正文”的系统规则；
- 禁止流式回答输出 JSON、代码块和协议字段；
- 加载旧历史时自动解析 JSON，只保留 `answer` 正文；
- 完整响应仍通过统一解析器提取图片和链接；
- 增加旧 JSON 历史兼容测试。

#### 主要修改文件

- `ai-service/app/core/llmchat.py`
- `ai-service/tests/test_llmchat_json.py`

#### 修复结果

流式聊天首个增量即为正常中文正文，不再向用户展示 JSON 协议外壳。

### 3.14 修复 AI 推荐数据库外商品和虚构参数

#### 问题现象

用户要求推荐商品时，模型会回答漫步者、小米等通用品牌型号，但这些商品并不存在于当前系统数据库中。

模型还可能把数据库中的“降噪”扩写为“主动降噪”，补充未提供的续航、材质或音频协议。

#### 原因分析

聊天功能此前只调用通用大模型，没有在回答前检索商品向量库，也没有将 Java 数据库商品摘要注入提示词。

此外，相对商品链接 `/api/v1/products/{id}` 未被链接提取器识别，前端无法生成真实商品卡片。

#### 修复内容

- 每轮聊天先使用用户当前问题和最近上下文查询 ChromaDB；
- 最多召回 5 件候选商品；
- 按商品 ID 调用 Java 内部接口读取真实名称、价格、库存、分类、标签、评分、销量和详情链接；
- 过滤已经下架的商品；
- 将候选商品放入受约束的 `<catalog>` 上下文；
- 强制模型只能推荐候选集中的商品；
- 没有匹配商品时，只能提供通用选购建议，禁止输出具体品牌和型号；
- 禁止把摘要中不存在的参数补充为事实；
- 推荐商品必须原样附带数据库详情页链接；
- 链接提取器增加 `/api/v1/products/{id}` 相对链接支持；
- Java 根据链接查询真实商品摘要并返回前端商品卡片。

#### 主要修改文件

- `ai-service/app/core/llmchat.py`
- `ai-service/app/api/py_api_server.py`
- `backend/src/main/java/com/aishop/modules/ai/AiChatService.java`
- `ai-service/tests/test_llmchat_json.py`

#### 修复结果

AI 推荐被约束在数据库在售候选商品内，回答可关联真实商品卡片，不再自由生成平台外商品。

### 3.15 修复会话历史保存后无法恢复

#### 问题现象

AI 服务和 PostgreSQL 中已有聊天记录，但刷新聊天页面后侧栏为空；点击旧会话时，页面反而执行：

```text
messages = []
```

用户因此认为系统没有保存会话历史。

#### 原因分析

- Python 和 Java 均有写入逻辑，但后端缺少查询会话和消息的接口；
- 前端 `onMounted` 没有加载会话；
- 切换会话时只清空消息，没有查询历史；
- Java 将数据库写入异常静默忽略，无法定位表缺失或连接异常。

#### 修复内容

- 新增会话列表接口：

```text
GET /api/v1/ai/chat/sessions
```

- 新增指定会话消息接口：

```text
GET /api/v1/ai/chat/sessions/{sessionId}/messages
```

- 查询接口按当前登录用户隔离数据并校验会话归属；
- 页面进入时自动加载会话列表并恢复最近会话；
- 点击侧栏会话时加载对应历史消息；
- 历史 AI 消息重新关联推荐商品卡片；
- 首次提问后将“新对话”更新为问题摘要；
- 每轮消息更新会话的 `updated_at`，最近会话优先展示；
- 数据库读写异常增加警告日志；
- PostgreSQL 实际检查确认 `chat_sessions` 和 `chat_messages` 表存在。

#### 主要修改文件

- `backend/src/main/java/com/aishop/modules/ai/AiChatController.java`
- `backend/src/main/java/com/aishop/modules/ai/AiChatService.java`
- `backend/src/main/java/com/aishop/modules/ai/dto/ChatHistoryMessageResponse.java`
- `frontend/src/services/api.ts`
- `frontend/src/views/AIChatView.vue`

#### 修复结果

刷新页面和切换会话后可以恢复历史记录。实际数据库检查时已有 9 个会话和 32 条消息，其中用户 `u10003` 有 6 个会话和 26 条消息。
